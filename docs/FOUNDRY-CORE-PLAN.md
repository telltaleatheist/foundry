**Step 3 as built, where it differs from §6/§7 below:**

- **Consumption by `app/`**: not a pinned tarball. `app/package.json` has
  `"@owen/foundry-core": "file:../packages/foundry-core"` with `install-links=true` in
  `app/.npmrc`, so npm installs a packed COPY (no junction, no lockfile integrity churn on
  every change); `app/tools/sync-foundry-core.cjs` rebuilds the package and refreshes the copy,
  and `build:electron` runs it first. bun's tests resolve the package to `src/` through
  `app/tsconfig.json` `paths` (emptied for Angular in `tsconfig.app.json`), so the app-side
  test (`hosted-runner`) and the library share module instances. BookForge (step 4) is the
  one consumer that pins a tarball.
- **Peers** are `^` ranges (`^2.0.34`, `^0.1.0`), not exact, so `adopt-crucible-release`'s
  `npm install` in `app/` is not refused before the package is repointed; they are also
  devDependencies naming `../../app/vendor/*.tgz`, and `app/test/crucible-pin.test.ts` fails
  until both follow an adoption. `@anthropic-ai/sdk` stays unlisted (tool-loop's optional peer;
  nothing installs it).
- **Tests**: `test/**` → `packages/foundry-core/test/engine/`, library `app/test/*` →
  `packages/foundry-core/test/lib/`; `app/test` keeps `hosted-runner` (imports `mount.ts`),
  `crucible-pin`, `lib-no-electron`.
- **Exports**: `./node/*` deep paths, no `./node` barrel; `./host` and `./engine` are the same
  modules as `node/host` and `node/engine`. The ES build is for bundlers (extensionless imports).
- **Package is `"type": "module"`** (dist/ gets `{"type":"commonjs"}`, dist/esm `module`), because
  esbuild bundles the engine's ES modules in node mode only under a module-typed package — the
  repo root was; without it the bundle's CJS interop changes.
- `tools/build-engine.mjs` moved into the package's `tools/` and gained `absWorkingDir: repo`
  (the metafile keys no longer depend on the directory it is started in). The engine's version
  is still the REPO's package.json (`src/engine/version.ts`), the one import that leaves the
  package. Root `package.json` lost the engine's dependencies; root `tsconfig.json` checks
  `tools/` only and `npm run typecheck` runs the package's programs first.
- No source maps in the package build (the app's main build had them); the tarball ships no `src/`.

## 3. The engine: spawned bundle or imported functions?

**Keep it a spawned bundle, owned and built by the library.** What forces a separate process
(tools/build-engine.mjs header, engine.ts):

1. File work is **synchronous and CPU-heavy** (zip/EPUB/PDF text layers, the 3,348-line number normaliser…) —
   in-process it would freeze Electron's main thread and every window's IPC.
2. **Cancel = kill the tree.** A run's children (the Python VLM helper from vlm/bridge.ts) die with it; there
   is no cooperative cancellation through the engine.
3. **Per-run credential in the environment** (`extraEnv`) and process-global state per run.
4. Progress on stderr + exit code is the contract both hosts' parsers rely on (`engine.ts` and BookForge's
   `foundry-host-queue.ts parseFoundryProgressLine`, `foundry-bridge.ts runFoundry`).
5. `process.exit` in cli.ts, module-level state in commands.ts.

Bun is **not** a reason (no Bun APIs). The build-time `with {type}` imports mean the engine cannot be emitted
by plain `tsc` — it stays an esbuild bundle (`build-engine.mjs` unchanged in substance).

What *can* become imported functions, cheaply and later: pure helpers the app already re-implements or mirrors
(`translate/languages.ts`, `clean/forms.ts` readers, `epub/xml.ts`, `vlm/contract.ts` types, the
`DEFAULT_NORMALIZER_MODEL` constant BookForge mirrors in narration-clean-text.ts). Export them from an
`engine-lib` subpath as ESM — but only the side-effect-free ones; nothing that writes files in a loop.

The library exports `engineCommand()` / `engineBundlePath()` with the bundle path resolved by
`require.resolve('@owen/foundry-core/engine/foundry-engine.cjs')` instead of `__dirname/../../engine`
(engine.ts:57 and bookforge foundry-bridge.ts:91). `FOUNDRY_BIN` override keeps working. Packaged in
`app.asar` is fine: Electron-as-Node reads asar, the fonts are read via fs, the .py is written out.

## 4. `app/shared/**` and the renderer

The renderer needs 33 of 42 shared files; all 42 are node-free, so the whole folder becomes the lib's
`shared/*` subpath, built **twice**: ESM for the Angular build (esbuild resolves package `exports`), CJS for
main (main is `module: CommonJS`). `@owen/tool-loop` already does exactly this dual build
(`tsconfig.esm.json` + `tsconfig.cjs.json` + `stamp-module-type.mjs`) — copy its scripts.

Two JSON files (`foundry.module.json`, `model-lineup.json`) are imported with `resolveJsonModule`; both builds
must copy them (bookforge `.gitattributes` marks them `-text`, keep that in the foundry repo too).

Renderer change is mechanical: `@shared/x` → `@owen/foundry-core/shared/x` (or keep the `@shared/*` alias and
repoint it to the package — fewer diffs, recommended for step 3).

Add a keeper: no file under the lib's `shared/` imports `node:*`, `electron`, or anything outside `shared/`.

also needs `app/shared` and the main-process LIB, and a root package that is also not-a-workspace and holds
`bun.lock` + `package-lock.json` is the confusing state the repo is already in.)

**Exports** (keep it to five; feature subpaths over a tangled graph are cosmetic — `job-queue.ts` imports
book, workspace, projects, crucible-dispatch, engine, env-install… so "clean" cannot be loaded without
"queue" anyway):

| Subpath | Built as | Who |
| --- | --- | --- |
| `@owen/foundry-core/shared/*` | ESM + CJS, d.ts | both renderers, both mains |
| `@owen/foundry-core/browser/*` | ESM | renderers (rectify, geometry) |
| `@owen/foundry-core/node` (+ `node/*` deep paths for the CLI) | CJS, d.ts | both mains, BF CLI |
| `@owen/foundry-core/host` | CJS types+fns | the host contract (FoundryHost, HostOperation, host queue) |
| `@owen/foundry-core/engine` | `engineCommand()`, `engineBundlePath()`, `runEngine()`; the `.cjs` bundle file itself | both mains, BF foundry-bridge |

An `init({ userDataDir, tempDir, broadcast, image })` (the **platform port**) is the only thing an app must
call before using `node`. That object is exactly the four Electron edges found in §1c.

**Build:** `tsc` (two configs, tool-loop style) for shared/browser/node into `dist/`; `build-engine.mjs` for
`engine/`. Both outputs ship in the tarball (like tool-loop ships `dist` + `src`).

**Dependencies the package owns:** `@crucible/client`, `@crucible/bootstrap`, `@owen/tool-loop` (all as
`file:vendor/*.tgz` inside the package), `pdf-lib`, `@pdf-lib/fontkit`, `libheif-js`, `undici`, `diff`.
Engine deps are bundled into the `.cjs`, so for the bundle they are devDependencies; for `node/` they are
dependencies. `@anthropic-ai/sdk` is an *optional peer* of tool-loop — is it actually installed? Foundry's app
does not list it; Ask's Claude path presumably goes over fetch in `cloud-providers.ts`. Decide explicitly:
either list it as a dependency of the package or keep tool-loop's Anthropic path unused; do not let it be
satisfied by accident from a host's node_modules.

**Nested tarballs are a problem:** a package whose dependencies are `file:vendor/x.tgz` inside it does not
install cleanly from its own tarball (npm resolves `file:` relative to the consumer for transitive deps in
some versions, and lockfile integrity breaks). Options: (a) the Crucible SDKs and tool-loop become
**peerDependencies** of foundry-core, and each app keeps pinning them in its own `vendor/` as today (BF already
does, same 2.0.34) — recommended, and it also solves the single-instance hazard; or (b) publish to a private
registry. Electron, Angular, rxjs, pdfjs-dist stay app-only.

**Consumption:**
- Foundry `app/`: `"@owen/foundry-core": "file:../packages/foundry-core"` (a directory dep inside one repo) —
  BUT the `_crucibleClientNote` says directory deps are not supported, and on Windows npm makes it a junction
  (CLAUDE.md worktree-hygiene hazard: recursive deletes and `git worktree remove` follow it). Safer and
  uniform: Foundry's app also pins a packed tarball, produced by `npm pack` in `packages/foundry-core`, with
  a dev script that repacks + reinstalls (`npm run core:relink`). `electron:dev` builds core first.
- BookForge: `"@owen/foundry-core": "file:vendor/owen-foundry-core-<ver>.tgz"`, adopted by a
  `tools/adopt-foundry-core.mjs` cloned from `tools/adopt-crucible-release.mjs` (which already finds
  package.json + prose key rather than assuming). Unreleased-core testing = the adopt script pointed at a local
  tarball path. This replaces re-vendoring; the commit stream `chore(foundry-app): vendor <sha>` becomes
  `chore: foundry-core <ver>`.

## 8. Candid notes on the decision

- **"Every feature in the library" is right for main-process logic and the engine — that's already ~90% of
  it, and the cuts are few (4 Electron edges, ipc.ts bodies).** It's mostly a *move*, not a redesign.
- **Feature subpaths are not real** with this graph: job-queue is a 7.8k-line hub importing almost everything.
  Promising "turning a feature on is just UI wiring" is true (the handlers exist in both apps); promising
  feature-level modularity is not, without breaking up job-queue — a separate project.
- **Two UIs = the renderer forks**, which is the real cost. 64.6k lines of Angular will diverge from day one
  (rulings 1 and 2 already diverge them), and every Foundry UI improvement becomes a manual port to BF's copy —
  re-vendoring by hand in a new form. If Owen wants Ask/analysis UI improvements in both, consider sharing the
  *component* layer too (an Angular library both import), with per-app shells. At minimum, share
  `shared/api.ts` + the pure renderer modules (step 2).
- **The renderer logic that matters (replay, edition, analysis arithmetic, rectify) is small**; keep it in the
  lib so the two windows can't draw the same book differently.
- **Keep the engine as a process.** Importing it into Electron main would be a regression (frozen UI, no
  kill-cancel).
- "Exactly as today" and rulings 1/2 conflict on purpose — do them as step 5, after the identity gate, or the
  move can't be verified.
- The `mount` seam (host socket: host-ops, host queue, onExport) stays useful even after BF owns its window
  — it's the clean line between "Foundry's book logic" and "BookForge's audio work". Don't dissolve it just
  because both sides are now BF code.
